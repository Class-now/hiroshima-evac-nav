# 河川水位（DoboX）の取り込みと毎日の更新

## 何をしているか

`scripts/build_river.py` が DoboX の 2 つのデータセットから `data/river.json` を作る（標準ライブラリだけ）。

| データセット | 中身 | 使い方 |
|---|---|---|
| [観測情報_観測所一覧](https://hiroshima-dobox.jp/datasets/1274)（河川課） | 県内の観測所（雨量・水位・ダム・潮位など 634 か所）の番号・名前・位置・基準水位。リソースは 1 つ（`河川_観測情報_観測所一覧_2026-10-21`） | 地図の「水」マーカーの位置と、基準水位との比較 |
| [観測情報_水位日集計](https://hiroshima-dobox.jp/datasets/1437)（河川課） | 1 日 1 ファイル（`河川_観測情報_水位日集計_YYYY-MM-DD`）。水位観測所 181 か所の 10 分ごとの水位 | 当日のファイルの、値のある最後の時刻の水位（最新）と、その日の最高値とその時刻 |

- 範囲は広島市の中心部とその上流側（`BBOX`）。2026-10-22 の取得で 37 か所（うち水位の値があるのは 36 か所。長和久(国) は終日欠測）。
- 基準水位（水防団待機・氾濫注意・避難判断・氾濫危険）との比較で `stage` 0〜4 を付け、地図の色にする（レベル2 黄・レベル3 赤・レベル4 紫に合わせた）。基準水位が無い観測所は灰色。
- **リアルタイムではない。** DoboX の当日のファイルは 10 分ごとの値で当日中も更新されるが、`data/river.json` は取り込んだ時点の値（毎日 1 回の更新）。アプリでは「◯月◯日の記録です。いまの水位ではありません」と時刻つきで出し、[広島県河川防災情報システム](https://www.kasen-bousai.pref.hiroshima.lg.jp/)へのリンクを付けている。

## 実データで確かめたこと（2026-10-22、日本国内の PC から取得）

- DoboX は **日本国外からのアクセスを 403 で拒否する**（AWS のロードバランサーが返す。GitHub の `ubuntu-latest` ランナー〈米国〉からも、このリポジトリを作業したクラウド環境からも同じ）。日本国内の PC からは取得できる。
- 文字コードはどちらも **UTF-8（BOM 付き）**。`decode()` は UTF-8 → cp932 の順に試す。

### 観測所一覧（datasets/1274、resource 39775）

- **ヘッダーが 3 行**。1 行目は列の区分（「（その他の各属性項目）」）、2 行目はその中の区分（「水位」「ダム」「潮位」）、**3 行目が列名**。`find_header()` が先頭 10 行から、観測所番号・観測所名・緯度・経度の列がそろう行を列名の行として選ぶ。
- 列名: データ種別, 集計連携用事務所名, 管理事務所番号, 管理事務所名, 所管事務所番号, 所管事務所名, データ所管番号, データ所管, 水系番号, 水系名, 水系名(表示用), 河川番号, 河川名, 河川名(表示用), 観測所番号, 観測所名, ふりがな, 市町村コード, 市町村名, 住所, 緯度, 経度, 零点高[T.P.m], 水防団待機[m], 氾濫注意[m], 避難判断[m], 氾濫危険[m], 洪水量[m3/s], 最低水位[EL.m], 制限水位[EL.m], 常時満水位[EL.m], ただし書き操作開始水位[EL.m], サーチャージ水位[EL.m], 注意潮位[TP.cm], 警戒潮位[TP.cm]。
- 「データ種別」は数字。**4 が水位**（181 か所。基準水位があるのは 4 だけで、水位日集計の観測所 181 か所と 1 対 1 に対応する）。ほかは 1（401 か所、雨量とみられる）、7（18 か所、ダム。常時満水位などの列がある）、12（13 か所、潮位。注意潮位の列がある）、13（21 か所、気象台など）。
- **「観測所番号」は所管ごとの番号で、県全体では重複する**（例: 国土交通省の 1 は三篠橋(国)〈太田川〉と山手(国)〈芦田川〉、雨量の戸山(国) にもある）。そのため「集計連携用事務所名（末尾の「事務所」を除く）/データ所管/観測所番号」を観測所のキーにしている（`river.json` の `code`、例 `西部建設/国土交通省/1`）。この組は重複しない。
- 緯度・経度は 10 進の度（測地系の記載は無い。三篠橋・祇園大橋などは実際の橋の位置とおおむね合うので、世界測地系とみなしている）。
- 基準水位は観測所によって一部だけ（例: 温品は氾濫注意・避難判断・氾濫危険だけ、段原は氾濫危険だけ）。無い段階は飛ばして比べる。範囲内 37 か所のうち 12 か所は基準水位が無く、灰色で出る。

### 水位日集計（datasets/1437）

- **観測所が列方向に並ぶ横持ち**。1 列目が行の見出しで、事務所名（「西部建設」など）・データ所管・水系名・河川名・観測所番号・観測所名・観測時刻 の 7 行。そのあと **10 分ごと（00:00〜23:50）の行**が続き、観測所ごとに「水位[m]」「フラグ」の 2 列（181 か所 × 2 列 + 1 = 363 列）。
- 欠測などは数値の代わりに `**`（フラグ 0xbe000000）、`--`（0xa0000000）、`CC`（0x8c000000）が入る。数値の行のフラグは 0x00000000・0x00400000・0x00880000 など（意味は公開されていない。数値はすべて使っている）。終日 `CC` の観測所（長和久(国) など 6 か所）は値なしとする。
- 水位は観測所ごとの零点高からの高さ（m）で、基準水位と同じ基準。潮の満ち引きで負の値もある。
- **当日のファイルも当日中に更新される**。10/22 21:29 に取得した 10/22 のファイルには 21:20 までの値が入っていた（応答の Last-Modified は取得した時刻）。過去の日（10/11〜10/20 を確認）は 00:00〜23:50 がそろう。ただし 10/21 のファイルは 10/22 21:30 の時点でも 20:50 までだった（その日の途中で更新が止まることがある）。
- `build_river.py` は当日と前日のファイルを取り、観測所ごとに日時が新しいほうを使う（当日のファイルがまだ空の早朝のため）。
- **リソースの並びは日付の古い順で、ページに 10 件ずつ**（2026-10-22 時点で 962 件、97 ページ。2024-01-25 から、ところどころ抜けあり）。1 ページ目だけを見ると 2024-03-14 が「最新」に見える（最初の取り込みで起きた）。`latest_resources()` は 1 ページ目のページ送り（`?page=N`）の最大番号を読み、最後のページ（と、その前のページ）から日付の最も新しいものを選ぶ。「まとめてダウンロード」（`/resource_bundle_download/1437`）は件数が多く 504 になるので使わない。DoboX の API は利用申請が要る（`/pages/developer`）ので使っていない。
- リソースのページ（`/resources/<id>`）には「最終更新」「作成日」「形式 CSV」があるだけで、更新頻度の記載は無い。

### 利用条件

- データセットのページにはライセンスの個別の記載が無い。ページ上部に「オープンデータは、商用・非商用を問わずだれでも自由に利用できます」とある。
- [DoboX の利用規約](https://hiroshima-dobox.jp/pages/terms)に、コンテンツは **CC BY 4.0** に従って利用でき、出典は「広島県インフラマネジメント基盤」（または「広島県インフラマネジメント基盤」と「データ管理者」）を記載する、とある。アプリの出典表示は「出典 広島県インフラマネジメント基盤（DoboX）／広島県「観測情報_観測所一覧」「観測情報_水位日集計」（加工して作成）」で、これに合っている。
- 規約には「上位規約等が定められているコンテンツはそれに従う」ともある。水位日集計には国土交通省（「(国)」の付く観測所）のデータも入っている。データセットとしては河川課が CC BY で出しているので、そのまま使っている。

## 手で取り込むとき（日本国内の PC で）

```bash
cd hiroshima-evac-nav
python3 -I scripts/build_river.py --raw /tmp/river --fetch --inspect   # 取得して、列の対応と観測所数を表示
python3 -I scripts/build_river.py --raw /tmp/river                     # data/river.json を作る
python3 -m unittest discover -s test -p "test_*.py" && npm test
```

`--inspect` は、観測所一覧の列名の行と各列の対応（`code -> 観測所番号` など）、水位の観測所数、水位日集計の観測所数と最新時刻、一覧に無い観測所を出す。DoboX の CSV の形が変わったら、ここで分かる。

## 毎日の更新（どれか 1 つ）

### A. 手元の PC で cron / launchd（いちばん簡単）

`sh scripts/update_river.sh` が 取得 → 生成 → テスト → コミット → push をする。Mac の例（毎日 9:20）:

```
crontab -e
20 9 * * * cd $HOME/path/to/hiroshima-evac-nav && /bin/sh scripts/update_river.sh >> /tmp/river.log 2>&1
```

Windows（この PC の運用、2026-10-22〜）: タスクスケジューラの `hiroshima-river-update` が毎日 9:20 に次を窓なしで動かす。`python3` は Microsoft Store のスタブなので `PYTHON=python` を渡す。ログは `~/.config/agent-notify/river-update.log`。

```
conhost.exe --headless "C:\Program Files\Gitinash.exe" -lc "cd '/c/For Claude/hiroshima-evac-nav' && PYTHON=python sh scripts/update_river.sh >> ~/.config/agent-notify/river-update.log 2>&1"
```

チェックアウトしているブランチに push する。PR #1 をマージしたら、この作業ツリーを main に切り替える。

PC が起きている日だけ更新される。push 先のブランチ（main に直接か、更新用ブランチか）は PM と決める。

### B. GitHub Actions ＋日本国内のセルフホストランナー

`.github/workflows/river-data.yml` は毎日 09:17 JST に動く。ただし **リポジトリ変数 `RIVER_RUNNER` が空のあいだはジョブを飛ばす**（GitHub のランナーでは 403 になるため）。

1. 日本国内のマシンにセルフホストランナーを登録する（Settings → Actions → Runners）。
2. Settings → Secrets and variables → Actions → Variables に `RIVER_RUNNER` = `self-hosted`（またはランナーに付けたラベル）を作る。
3. Actions タブから `river-data` を手動実行（workflow_dispatch）して確かめる。

注意: **public リポジトリでのセルフホストランナーは、フォークからの PR でランナー上のコードが動く危険がある**。使う場合は Settings → Actions → General で「Fork pull request workflows」の承認を必須にし、ランナーをこのワークフロー専用のラベルにする。心配なら A を使う。

### C. 日本リージョンのクラウドで動かす

GitHub ではなく日本リージョンの実行環境（クラウドの定期実行など）で `update_river.sh` を動かす方法もある。費用と鍵の管理が増えるので、MVP では A を推す。
